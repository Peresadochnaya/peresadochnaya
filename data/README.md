# Модуль данных GTFS

## Версионное хранилище в k3s

Периодический Job запускает из корня проекта:

```bash
python -m data.gtfs.versioned_static --store-dir /data/gtfs
```

Расписание Kubernetes — каждые 20 минут; сам скрипт выполняет ровно одно обновление. Доступ к API портала выполняется с проверкой TLS. При наличии серверных `ETag`/`Last-Modified` следующий запрос использует условные заголовки. Без них ZIP скачивается и сравнивается по SHA-256.

Структура постоянного тома:

```text
/data/gtfs/
  versions/<sha256>/feed.zip
  versions/<sha256>/tables/*.csv
  versions/<sha256>/manifest.json
  current.json
  refresh-status.json
```

Сначала полностью подготавливается каталог снимка, затем атомарно меняется `current.json`. После успешной публикации прежние каталоги удаляются: на диске остаётся только последний GTFS. API читает самодостаточный `current.json` для статуса; читателю ZIP/CSV при исчезновении старого каталога следует перечитать указатель и повторить открытие. Одинаковый ZIP повторно не распаковывается. На каждый запуск, включая HTTP 304, календарь повторно проверяется на текущую московскую дату.

`current.json` содержит `sha256`, `checked_at`, `service_date` (`YYYYMMDD`), `usable`, `active_service_ids`, `routes`, `stops`, `invalid_calendar_rows`, `latest_exception_date`, `warning`. `usable=false` означает отсутствие действующих service_id на дату проверки. Такой структурно корректный ZIP сохраняется для исследования, но не должен автоматически активировать граф OTP. Метаданные внутри версии отражают дату её первоначального получения; для сегодняшней пригодности используется `current.json`.

`refresh-status.json` содержит `status` (`running`, `updated`, `unchanged`, `error`), `attempted_at`, `last_success_at`, `checked_at`, `sha256`, `error`, `etag`, `last_modified` и метаданные последнего успешного результата. Все временные строки — ISO 8601 с часовым поясом. При ошибке предыдущий `current.json` остаётся доступен, а `last_success_at` сохраняется. Ошибка пишет сообщение в stderr и возвращает код 1.

Обновления защищены неблокирующим файловым `flock`, независимо от настройки CronJob. История GTFS и pin версии OTP не хранятся. При провале загрузки или подготовки текущий снимок остаётся доступен; временные файлы удаляются. API монтирует том только для чтения. Перестроение и переключение графа OTP — отдельная задача: загрузчик GTFS их не выполняет.

## Передача GTFS в OTP

Модуль `otp` не копирует GTFS из `data/gtfs` вручную: `otp/scripts/graph_store.py prepare`
читает `data/gtfs/current.json`, открывает `versions/<sha256>/feed.zip` и работает
с копией в собственном `staging`. Контракт этого хранилища не меняется.

Что важно при таком чтении:

- `prune` удаляет предыдущий снимок сразу после публикации нового. Копирование
  может попасть в этот момент, поэтому `prepare` при `ENOENT` перечитывает
  `current.json` и повторяет попытку (до пяти раз с интервалом 1 с). Ошибкой это
  не считается.
- SHA-256 скопированного файла сверяется с `sha256` из `current.json`. Расхождение
  останавливает подготовку: граф не должен собираться из неподтверждённого файла.
- Имя файла внутри `otp/staging` обязано содержать `gtfs` (`feed.gtfs.zip`): OTP
  определяет тип входа по имени, а не по содержимому.
- Исправление календаря применяется только к копии в `otp/staging`. Исходный ZIP
  в `versions/<sha256>/feed.zip` остаётся байт-в-байт таким, каким пришёл с портала.
  В `otp/data/current.json` сохраняются оба хэша: `gtfs_source_sha256` и
  `gtfs_fixed_sha256`.
- `active_service_ids=0` и `usable=false` относятся к дате проверки, а не к
  произвольной дате запроса. Решение о пригодности конкретной даты принимает
  OTP (`OUTSIDE_SERVICE_PERIOD`), а не этот загрузчик.
- Обновление GTFS само по себе не пересобирает граф и не переключает его.
  Пересборка запускается отдельно (`otp/scripts/build-graph.sh`), а backend
  видит расхождение `gtfs_source_sha256` графа с текущим `sha256` и сообщает
  предупреждением в `/api/v1/data/status`.

Пути в таблице указаны от каталога `data`. Команды ниже запускайте из корня репозитория; его локальное имя может быть любым.

## Подготовка после клонирования

Проверено на Python 3.14. Из корня репозитория создайте окружение и установите зависимости:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r data/requirements.txt
```

ZIP вручную скачивать не нужно: `.venv/bin/python data/gtfs/refresh_static.py` получит его с портала и построит CSV. Для `live_vehicles.py` нужен доступ к порталу и установленные зависимости; ZIP ему не требуется. Публичный CA-файл уже лежит в `data/gtfs/certs/`. Текущий `raw/portal-gtfs.zip` можно передать команде через Git; резервный ZIP и подготовленные CSV игнорируются.

Обновить их из корня проекта:

```bash
.venv/bin/python -m data.metro.official_reference
```

Дата окончания действия опубликованных таблиц не указана. CSV не содержат полного расписания рейсов и времени пути между станциями.

**Контракт для backend:** читать `manifest.json` и сверять SHA-256 файлов перед загрузкой. `stations.csv.station_id` — ключ станции в этом наборе; `station_hours.csv.station_id`, `segments.csv.from_station_id`/`to_station_id` и `transfers.csv.station_a_id`/`station_b_id` ссылаются на него. В `segments.csv` и `transfers.csv` каждая пара записана один раз, связь двусторонняя. `boarding_allowed=0` запрещает посадку/высадку на закрытой станции, но она остаётся на линии между соседями. `intervals.csv` задаёт **диапазон**, а не точное время отправления или постоянный интервал. `station_hours.csv` содержит отдельные строки вестибюлей; первые и последние поезда указаны в сторону `first_terminus` и `second_terminus`, а `odd`/`even` означают чётность поезда в исходной таблице. Оценку времени пути и правила праздников backend определяет отдельно и помечает как оценочные.

Для полноценного GTFS метро нужны фактические рейсы или проверенные времена хода между станциями и календарь исключений. До получения такого источника эти CSV нельзя загрузить в OTP как расписание поездов.

Классов в этом модуле нет. Основные функции:

| `refresh_static.prepare_csv` | Извлекает таблицы `.txt` как `.csv`, сохраняет хэш ZIP в manifest |
| `refresh_static.activate_archive` | Заменяет ZIP и сохраняет одну предыдущую версию |
| `refresh_static.main` | Скачивает ZIP и печатает JSON с результатом |
| `live_vehicles.build_snapshot` | Разбирает protobuf и формирует JSON с возрастом каждой позиции |
| `live_vehicles.fetch_snapshot` | Запрашивает свежий protobuf по HTTPS |
| `live_vehicles.show_positions` | Печатает человекочитаемый список машин |
| `live_vehicles.moscow_time` | Форматирует Unix-время для консоли |
| `live_vehicles.main` | Обрабатывает параметры CLI и выводит снимок или JSON Lines |
| `metro.official_reference.extract_intervals` | Переносит опубликованные диапазоны интервалов без расчёта рейсов |

## Контракт для backend

В проекте два входа: GTFS Schedule ZIP для OTP и GTFS-RT Vehicle Positions для backend. Собственного HTTP API и запущенного OTP в `data` нет.

### 1. GTFS Schedule → OTP

```bash
.venv/bin/python data/gtfs/refresh_static.py
```

Скрипт получает `https://transport.orgp.spb.ru/Portal/transport/internalapi/gtfs/feed.zip`, проверяет TLS и ZIP, сохраняет его в `raw/portal-gtfs.zip`, а все таблицы `.txt` извлекает в `processed/gtfs/` с расширением `.csv`. Содержимое CSV не меняется. При изменении прежний ZIP остаётся в `raw/portal-gtfs.previous.zip`.**Выход:** одна строка JSON в `stdout`; при ошибке — сообщение в `stderr` и код процесса `1`.

```json
{"status":"unchanged","sha256":"<hash>","previous_sha256":"<hash>","routes":547,"stops":8811,"invalid_calendar_rows":1013,"active_service_ids":0,"latest_exception_date":"20261104","service_date":"20261110","warning":"Нет действующих service_id на указанную дату","csv_status":"updated","csv_dir":"<data-path>/processed/gtfs","csv_files":14,"checked_at":"<ISO-8601>","archive":"<data-path>/raw/portal-gtfs.zip"}
```

| Поле | Действие команды |
| --- | --- |
| `status=updated` | Передать новый ZIP планировщику и пересобрать граф OTP |
| `status=unchanged` | Использовать текущий граф, если он уже построен из этого `sha256` |
| `csv_status=updated` | Перечитать подготовленные CSV; бывает и при первом запуске с неизменным ZIP |
| `csv_status=unchanged` | Подготовленные CSV уже соответствуют `sha256` |
| `active_service_ids=0` или `warning` | Не считать расписание пригодным для поездок на `service_date`; проверить источник |
| Код процесса `1` | Оставить прежний ZIP и граф; зарегистрировать ошибку |

OTP использует `routes.txt`, `stops.txt`, `trips.txt`, `stop_times.txt`, календарь и геометрию из ZIP. Для маршрута от координаты A до B дополнительно нужен OSM PBF. На **11 ноября 2026 года** в наземном архиве нет активных `service_id`; транспортных вариантов на эту дату OTP может не вернуть. Оценочный GTFS метро собирается отдельным updater, описанным ниже.

Backend может читать `processed/gtfs/routes.csv`, `stops.csv` и другие таблицы через `csv.DictReader(..., encoding="utf-8-sig")`. Перед использованием он сверяет `manifest.json.source_sha256` с `sha256` текущего ZIP. Не сканируйте многомиллионный `stop_times.csv` на каждый HTTP-запрос: построение маршрута остаётся задачей OTP.

### 2. GTFS-RT → backend

Один снимок всех машин:

```bash
.venv/bin/python data/gtfs/live_vehicles.py --all --json
```

Троллейбус №31:

```bash
.venv/bin/python data/gtfs/live_vehicles.py --route-id 1087 --json
```

Непрерывно: `.venv/bin/python data/gtfs/live_vehicles.py --all --json --watch 30`. Каждая строка `stdout` — **отдельный JSON-снимок**, без предыдущих снимков. `--all` снимает фильтр. Скрипт сам обращается к `https://transport.orgp.spb.ru/Portal/transport/internalapi/gtfs/realtime/vehicle`; предварительный `curl` не нужен.

**Контракт JSON:**

```json
{
  "source_url": "https://transport.orgp.spb.ru/Portal/transport/internalapi/gtfs/realtime/vehicle",
  "gtfs_realtime_version": "1.0",
  "fetched_at": 1794305262,
  "feed_timestamp": 1794305261,
  "feed_age_seconds": 1,
  "feed_is_stale": false,
  "route_filter": null,
  "vehicles": [{
    "vehicle_id": "26234", "label": "5101", "route_id": "1087",
    "trip_id": null, "stop_id": null,
    "latitude": 59.981716, "longitude": 30.328917,
    "bearing_deg": 49.0, "speed_mps": 3.333333,
    "observed_at": 1794305256, "age_seconds": 6, "is_stale": false
  }]
}
```

Это пример структуры, не текущие координаты. `feed_timestamp` — когда портал сформировал снимок; `observed_at` — когда измерены координаты **этой машины**; `fetched_at` — когда мы получили ответ. Все три поля — Unix seconds. `feed_age_seconds` и `age_seconds` показывают возраст в секундах на момент запроса. `feed_is_stale` и `is_stale` становятся `true`, если время отсутствует, старше 90 секунд или более чем на 30 секунд в будущем. Поэтому по `vehicle_id`, координатам и `observed_at` можно сказать, где и когда находилась машина. `/vehicle` отдаёт текущий снимок; для истории нужно сохранять последовательные ответы `--watch`.

Координаты — WGS84, скорость — м/с. `route_filter=null` при `--all`. Поля `trip_id`, `stop_id`, `bearing_deg`, `speed_mps`, `observed_at` могут быть `null`; `label` и `route_id` тоже могут отсутствовать в записи. `vehicles: []` означает, что по фильтру нет машин в этом снимке, а не ошибку запроса.

**Что делает backend с каждым снимком:**

1. Проверяет `feed_is_stale`; если `true`, не использует снимок как текущий.
2. Оставляет машины с `is_stale=false` и корректными координатами; проверяет аномальные скорости.
3. Сопоставляет `vehicle.route_id` со свежим `routes.txt` **той же версии ZIP** и отдаёт координаты фронту для карты.
4. При сетевой, TLS, HTTP или protobuf-ошибке не получает JSON, сохраняет последний снимок только с отметкой его возраста; следующий запрос делает через 30 секунд или позже.

В `/vehicle` нет надёжных `trip_id`, `stop_id`, готового ETA и поправки ко времени рейса. Позицию нельзя напрямую превратить в время прибытия или корректировку маршрута OTP.

### 3. Запрос маршрута A → B

Backend принимает от фронта `from: {lat, lon}`, `to: {lat, lon}` и время отправления с часовым поясом. Он запрашивает **запущенный командой OTP** через GraphQL, получает варианты `data.planConnection.edges[].node` и возвращает фронту их `legs` в порядке движения. Пример запроса к OTP 2 с координатами и датой, на которую в текущем ZIP есть активные `service_id`:

```bash
curl --request POST 'http://localhost:8080/otp/gtfs/v1' \
  --header 'Content-Type: application/json' \
  --data-binary @- <<'JSON'
{"query":"{ planConnection(origin: { location: { coordinate: { latitude: 59.9972, longitude: 30.2963 } } }, destination: { location: { coordinate: { latitude: 59.9431, longitude: 30.2789 } } }, dateTime: { earliestDeparture: \"2026-11-04T12:00:00+03:00\" }) { edges { node { start end legs { mode from { name } to { name } route { gtfsId shortName } } } } } }"}
JSON
```

`edges: []` означает, что вариантов не найдено; GraphQL `errors` или HTTP 4xx/5xx — ошибка запроса/сервера. Запрос проверен на локальном OTP 2.11 из `otp/` 11 ноября 2026 года: он вернул маршрут с пересадкой. Backend обращается к тому же эндпоинту через `backend/app/otp.py`; конфигурация OTP и версии графа описаны в `otp/README.md`. GTFS-RT позиции можно показывать рядом с маршрутом, но для переранжирования по пробкам backend нужна отдельная модель времени движения.

Адреса портала отвечали без токена при проверке 10 ноября 2026 года. [Официальные условия API](https://transport.orgp.spb.ru/help) отдельно предусматривают заявку и статический IP.


## Оценочный GTFS метро

```bash
python -m data.metro.refresh --store-dir /data/metro
```

Отдельный CronJob `metro-refresh` проверяет источники **каждые 20 минут**, через тот же
`HTTPS_PROXY`, что и наземный GTFS. Исходный экспорт Серафима
`data/metro/official_reference.py` и его CSV не перезаписываются. Новый updater
использует функции этого экспортера, получает свежие официальные страницы и
координаты HH, затем обогащает сеть временем из
[pMetro Metro.trp](https://github.com/pMetro/pMetro-maps/blob/master/maps/Peterburg/Metro.trp).
Для pMetro сначала определяется текущий commit SHA, после чего файл читается по
неизменяемой ссылке. SHA-256 каждого входа записывается в происхождение данных.

`Driving` в pMetro — минуты и секунды (`3.10` = 190 секунд), не десятичные минуты.
Ветвления учитываются: действующий перегон Горный институт — Спасская обходится
без посадки на будущей Театральной. В GTFS входят только станции и связи официальной
сети; будущие станции и нулевые placeholders pMetro не включаются. Для всех 69
перегонов и 10 пар пересадок требуется положительное время; при пропуске или
противоречии новый набор не публикуется. Обратное направление использует ту же
справочную длительность. У закрытых станций сохраняется проезд, но выставляются
`pickup_type=1` и `drop_off_type=1`; пересадки через закрытые станции исключаются.

Архив содержит 6 маршрутов, 75 станций, 36 шаблонов рейсов (два направления и три
типа дня), `stop_times.txt`, `frequencies.txt`, `calendar.txt`, `transfers.txt` и
служебные таблицы GTFS. `stop_times.txt` задаёт накопленные смещения от нуля без
добавочной стоянки; ожидание не прибавляется к времени проезда или перехода.
В `frequencies.txt` стоит `exact_times=0`, частота — округлённая вверх середина
официального диапазона интервалов. Это модель частоты, а не точные отправления и
не доказанное математическое ожидание ожидания. Окна ограничены опубликованными
интервалами и временем первых/последних поездов соответствующего направления с
конечной; для чётных/нечётных дат используется более позднее первое отправление.
Частоты применяются к обоим направлениям одинаково. Деповские рейсы, режим
праздников, время входа/выхода и точные стоянки неизвестны. Границы работы могут
быть неполными: updater не экстраполирует интервал за пределы опубликованных окон.

Календарь действует от даты сборки (не раньше даты действия официальных источников)
на 30 дней вперёд и обновляется ежедневно при очередной проверке. При смене формата
или дат официальных страниц строгий парсер останавливает обновление, чтобы не
подмешать старую или неправильно разобранную таблицу.

Хранилище такое же, как для наземного транспорта, но отдельное:

```text
/data/metro/current.json
/data/metro/refresh-status.json
/data/metro/versions/<sha256>/feed.zip
/data/metro/versions/<sha256>/manifest.json
/data/metro/versions/<sha256>/tables/*.csv
```

В ZIP дополнительно лежит `metro_reference.json`: обогащённые таблицы с
`duration_seconds`, `duration_source=pmetro`, ссылками, хешами источников и
предупреждениями о допущениях. Никакого GTFS-RT или официального точного расписания
этот файл не обещает. `usable=true` в указателе означает только наличие действующего
календаря; точность времени проверяется по происхождению и предупреждениям.

Публикация использует ту же блокировку и атомарный указатель, что и наземный GTFS.
При ошибке текущий ZIP остаётся на месте; после успеха старая версия удаляется.
Детерминированный ZIP не меняет SHA только из-за времени запуска. Сборка GTFS ещё
не запускает OTP и не изменяет ручку `/routes`: граф должен отдельно загрузить оба
архива (наземный и метро) вместе с OSM. Текущие GTFS HTTP-ручки читают прежний
наземный архив, объединение с метро в их выдаче пока не реализовано.

**Как метро попадает в OTP.** `otp/scripts/graph_store.py prepare` читает
`data/metro/current.json`, копирует фид в staging как `metro.gtfs.zip` и включает
его SHA-256 в версию графа. Поэтому обновление только метро требует пересборки:
`otp/scripts/build-graph.sh` (фид берётся из `data/metro` по умолчанию, отсутствие
фида — ошибка). Подробности и проверочные запросы — в `otp/README.md`.

Пересборка без сетевых запросов из сохранённых источников:

```bash
python -m data.metro.refresh --store-dir /tmp/metro-gtfs \
  --reference-dir data/processed/metro \
  --pmetro-file data/metro/tests/fixtures/Metro.trp
python -m pytest data/metro/tests
```

Тестовый TRP — зафиксированный пример pMetro, а не источник периодического обновления.

## Пригородные поезда: датированный GTFS для backend

`rail/refresh.py` получает расписания электричек через API Яндекс.Расписаний:
`schedule` для отправлений и прибытий, `thread` для всех остановок и времени,
`stations_list` для координат. Ключ берётся только из переменной
`YANDEX_RASP_API_KEY`; в файлы и Git он не записывается.

Получить ключ можно в [Кабинете разработчика Яндекса](https://developer.tech.yandex.ru/):
войти с Яндекс ID, подключить **API Яндекс.Расписаний** и взять ключ на вкладке
«Ключи». [Официальная инструкция](https://yandex.ru/dev/rasp/doc/ru/concepts/access).

### Расписание на неделю

Этот запуск получает расписание **только на неделю: 12–18 ноября 2026**.
Данные ограничены этими датами, потому что API возвращает расписание на
запрошенный день, а рейсы и отмены могут различаться по дням. Для следующей
недели нужно запрашивать новые даты. Результат — один GTFS ZIP; исходные
ответы сохраняются в `data/raw/rail/<дата>/`.

Из корня проекта в `zsh`:

```bash
read -rs "YANDEX_RASP_API_KEY?Ключ API: "; echo; export YANDEX_RASP_API_KEY
.venv/bin/python -m data.rail.refresh --date 2026-11-12 --days 7 --raw-only --resume
.venv/bin/python -m data.rail.refresh --date 2026-11-12 --days 7 --offline
```

Первая команда может выполнить несколько тысяч запросов `thread` и занять
значительное время. Каждый успешный ответ сразу сохраняется. При ошибке API
повторите её с `--resume`: уже сохранённые ответы за те же даты повторно не
запрашиваются. Вторая команда не использует сеть и переключает `current.json`
только после успешной сборки всех дней. Для следующей скользящей недели
запустите те же команды с новой датой начала. Текущие ответы не обновляются
автоматически после сборки; изменения расписания требуют повторного запроса
соответствующих дат. `--resume` сохраняет старые ответы и предназначен для
продолжения прерванной выгрузки, а не для проверки свежести.
Итоговый JSON содержит `daily` с числом рейсов по каждой дате; его можно
сверить с исходными ответами в `data/raw/rail/<дата>/`.

Если поезд прибывает после полуночи, API иногда возвращает 404 для `thread`
с датой прибытия. Скрипт тогда запрашивает дату отправления накануне и
принимает ответ только при совпадении времени и станции с расписанием.
`--resume` продолжит прерванную выгрузку; после неё `--offline` соберёт ZIP
из сохранённых ответов. Если оба ответа отсутствуют или не совпадают,
сборка остановится и прежний `current.json` останется на месте.

Ниже — одиночный запуск для одной даты; он по-прежнему поддерживается.

Из корня проекта в `zsh`:

```bash
read -rs "YANDEX_RASP_API_KEY?Ключ API: "; echo; export YANDEX_RASP_API_KEY
.venv/bin/python -m data.rail.refresh --date 2026-11-12 --raw-only
.venv/bin/python -m data.rail.refresh --date 2026-11-12 --offline
```

Первая команда получает и сохраняет исходные ответы, не пытаясь собрать GTFS.
Вторая строит GTFS из этих файлов без сети и ключа. Каждый успешный ответ API
**сразу** сохраняется в
`data/raw/rail/<дата>/schedule/`, `thread/` или `stations_list/` отдельным
JSON-файлом. Внутри файла — метод, параметры запроса без ключа, время получения
и ответ. Поэтому даже при ошибке сборки GTFS исходные данные остаются на диске.
Повторный обычный запуск использует ответы не старше часа. После ошибки можно
повторить вторую команду без сетевых запросов и без ключа:

```bash
.venv/bin/python -m data.rail.refresh --date 2026-11-12 --offline
```

Если для полной сборки какого-то ответа ещё нет, `--offline` сообщит, какого
именно; тогда запустите первую команду с ключом и `--resume`. Этот флаг
повторно использует все сохранённые ответы за дату независимо от возраста и
запрашивает только недостающие. Для рейсов, прибывающих сразу после полуночи,
скрипт дополнительно запрашивает `thread` за предыдущий день. В ответах
`thread` время приходит без смещения UTC; для этого набора оно сверяется с
расписанием станции и интерпретируется как московское время.

По умолчанию проверяются Московский (`s9602494`), Витебский (`s9602496`),
Финляндский (`s9602497`), Балтийский (`s9602498`) и Ладожский (`s9602499`)
вокзалы. Для другого набора укажите `--station s...` несколько раз.
Скрипт собирает **только рейсы, найденные на указанных станциях**; он не
гарантирует полный охват всех пригородных поездов СПб и Ленинградской области.
Если API ограничил результат и получить остальные страницы/направления не
удалось, скрипт завершится с ошибкой без публикации нового GTFS.

Локальный результат лежит в `data/processed/rail/`:

```text
current.json
refresh-status.json
versions/<sha256>/feed.zip
versions/<sha256>/tables/*.csv
versions/<sha256>/manifest.json
versions/<sha256>/source.json
```

`feed.zip` содержит GTFS Schedule: `route_type=2` (железная дорога),
`stops.txt` с координатами, `trips.txt`, точные `stop_times.txt` и
`calendar_dates.txt` **только на полученные даты рейсов**. При одиночном запуске
`source.json` содержит ответы и координаты использованных станций; при запуске
на диапазон — перечень дат и хэшей дневных сборок. Полные ответы всегда
лежат в `data/raw/rail/<дата>/`. При обновлении архив, CSV и `current.json`
публикуются по тому же контракту, что городской GTFS. Результаты API
игнорируются Git; их нельзя считать постоянным публичным источником данных.

**Контракт с backend:** текущий `backend/app/gtfs_store.py` читает только
`DATA_ROOT/gtfs/versions/<sha>/feed.zip`. Он уже распознаёт `route_type=2`
как `rail`, но отдельный каталог `rail/` автоматически не подключает.
Backend/OTP должны получить этот ZIP как второй фид или объединить его с
городским GTFS с сохранением уникальных `rail:` ID. До такой интеграции
электрички не появятся в ответах API маршрутов. Яндекс не предоставляет здесь
GTFS-RT положений электричек; время в ZIP — расписание, а не факт движения.
