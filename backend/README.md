# Backend API

Контракт для фронтенда. Адресные API и Road Router Яндекса проверены
11 ноября 2026 года четырьмя живыми вызовами через код ручек в pod API.
OTP подключён адаптером: реальные маршруты общественного транспорта работают
с `PLANNER_MODE=otp` и запущенным сервисом OTP.
Ручки, предполагающие обращения к Яндексу, принимают query-параметр `dummy`
с default `true`: без обращения к провайдеру возвращается явно помеченный
демонстрационный ответ на общем наборе GTFS.
Для реальной работы фронт должен явно передать
`?dummy=false`; если провайдер не настроен, это HTTP 503, без подмены заглушкой.
Правило действует на routes, road-route, suggest, geocode и reverse.
Dummy не выполняет текущую оценку дорожных условий или расписаний. Для
автобусных демо-сегментов используется GTFS-геометрия, для пеших подходов
и автомобильной демо-оценки — прямые линии. `PLANNER_MODE` описывает конфигурацию
планировщика, но не отменяет явное согласие на реальные запросы.

Из корня репозитория:

```sh
python3 -m venv backend/.venv
backend/.venv/bin/pip install -r backend/requirements-dev.txt -r data/requirements.txt
cd backend
PLANNER_MODE=dummy .venv/bin/uvicorn app.main:app --reload
.venv/bin/python -m pytest
```

С запущенным OTP из `otp/`:

```sh
cd backend
PLANNER_MODE=otp OTP_URL=http://localhost:8080 .venv/bin/uvicorn app.main:app --reload
```

**⚠️ Это не работает как описано без `DATA_ROOT`.** Приложение читает метаданные из `$DATA_ROOT/gtfs/current.json` и `$DATA_ROOT/otp/current.json`. В K8s PVC смонтирован в `/data`, а локально `/data` не существует. Без явного `DATA_ROOT` маршрутизация работает, но `GET /api/v1/data/status` возвращает `state=missing`, а в ответах маршрутов `gtfs_version` и `graph_version` будут `null`.

Локально создайте каталог-сборщик со ссылками на оба хранилища:

```sh
DR=$(mktemp -d)
ln -s "$(cd .. && pwd)/data/gtfs" "$DR/gtfs"
ln -s "$(cd .. && pwd)/otp/data"  "$DR/otp"
PLANNER_MODE=otp DATA_ROOT="$DR" .venv/bin/uvicorn app.main:app --reload
```

Теперь `/api/v1/data/status` отдаст версии, а каждый ответ маршрута будет содержать `gtfs_version` и `graph_version`.

`gtfs_version` остаётся `null`, пока в `data/gtfs` не опубликована версия — этот каталог изначально содержит только код скриптов. Публикация: `python -m data.gtfs.versioned_static --store-dir data/gtfs` (скачивает фид с портала ОРП). Граф при этом может быть собран из другого файла (`build-graph.sh --gtfs-zip`), и тогда `data/status` перейдёт в `degraded` с предупреждением `Graph was built from a different GTFS version` — это корректный сигнал расхождения, а не ошибка.

В Docker-контейнере (без K8s) смонтируйте оба каталога в `/data`:

```sh
docker build -f backend/Dockerfile -t peresadochnaya/api:local .
docker run --rm -p 8000:8000 \
  -e PLANNER_MODE=otp -e OTP_URL=http://host.docker.internal:8080 \
  -v "$(pwd)/data/gtfs:/data/gtfs:ro" \
  -v "$(pwd)/otp/data:/data/otp:ro" \
  peresadochnaya/api:local
```

Тесты OTP-адаптера офлайн: реальный ответ сохранён в
`app/fixtures/otp/plan-response.json`, сеть запрещена.

OpenAPI: `/openapi.json`, интерактивный контракт: `/docs`.

**Смысл флага сохранён:** `dummy=true` (по умолчанию) — согласованные
демо-данные без внешних вызовов; `dummy=false` — реальные источники и возможный
расход API-квот. Ответ демо остаётся помечен `mode=dummy`. Меняются сами
демо-данные; клиентам не требуется менять значение флага.
Единственный файловый контракт — корневой `openapi.yaml`. Он генерируется из моделей
FastAPI и общих описаний в `app/api_docs.py`; тест сверяет его с `/openapi.json`.
После изменения моделей из корня репозитория:

```bash
python backend/export_openapi.py
```

Нужны dev-зависимости backend. Ручное редактирование YAML отдельно от моделей
приведёт к ошибке проверки контракта в CI.

| Endpoint | Ответ |
| --- | --- |
| `GET /health/live` | Процесс жив |
| `GET /health/ready` | HTTP API готов; не гарантия готовности planner/GTFS |
| `GET /api/v1/data/status` | Версии GTFS/графа, состояние и предупреждения |
| `GET /api/v1/ticket-profiles` | Доступные профили проездных с `coverage_status=not_implemented` |
| `POST /api/v1/routes` | Маршруты либо отдельная диагностируемая ошибка |
| `GET /api/v1/suggest?q=...&limit=5&dummy=true` | Синтетические подсказки; `dummy=false` включает реальный режим |
| `GET /api/v1/geocode?q=...&dummy=true` | Адрес → координаты; вместо `q` можно передать `uri` |
| `GET /api/v1/reverse?lat=...&lon=...&dummy=true` | Координаты → адрес |
| `POST /api/v1/road-route?dummy=true` | Оценка автомобильного участка; `dummy=false` включает Router API |

Подсказки: `q` — строка 2–256 символов с непустым текстом, `limit` — 1–10,
по умолчанию 5. Поиск смещён к Санкт-Петербургу и Ленинградской области
прямоугольником `26.5,58.3~35.8,61.4`, без строгого административного ограничения.
Успешный ответ: `{"mode":"yandex","items":[{"title":"Пионерская","subtitle":"Санкт-Петербург","uri":"..."}],"warnings":[]}`.
`subtitle` может быть null; `uri` — непрозрачный идентификатор Яндекса для
последующего геокодирования выбранного результата. Координаты подсказка
не обещает. Нет совпадений — HTTP 200 с `items: []`. По умолчанию `mode=dummy`,
URI имеет префикс `dummy:`. Геокодер отклоняет dummy URI в реальном режиме
до любого обращения к провайдеру.

Геокодер принимает ровно одно из `q` (2–256 символов) или `uri` (до 4096).
Геокодер и reverse возвращают общий формат:
`{"mode":"yandex","items":[{"lat":59.956433,"lon":30.310138,"label":"Адрес","precision":"street"}],"warnings":[]}`.
`precision` может быть null; возвращается максимум один результат. Нет совпадений
— пустой `items`. Dummy geocode возвращает фиксированную демонстрационную точку,
dummy reverse — подпись с координатами без настоящего адреса. Reverse может найти
соседний дом: фронт использует его `label`, но сохраняет исходные координаты клика
как точку маршрута, а не незаметно заменяет их координатами найденного здания.

Настройка: `YANDEX_GEOCODER_API_KEY` и `YANDEX_SUGGEST_API_KEY` читаются из env.
В k3s они ссылаются на Secret `yandex-api`, ключи `geocoder` и `suggest`.
Ключи не передаются фронту. Нет ключа — 503 `address_provider_unavailable`,
квота/лимит — 503 `address_provider_quota`, таймаут — 504,
некорректный ответ или отказ провайдера — 502. Тексты ошибок не содержат URL,
ключей и исходного ответа провайдера. Один реальный вызов — максимум один
HTTP-запрос к Яндексу: без повторов, редиректов и фоновых проверок. Фронту стоит
делать debounce подсказок и не повторять запросы автоматически при ошибках.

Запросы составлены по документации
[Suggest](https://yandex.ru/maps-api/docs/suggest-api/request.html) и
[Geocoder](https://yandex.ru/maps-api/docs/geocoder-api/request.html).
Саджест использует `attrs=uri`, `types=geo`, `lang=ru`; геокодер —
`format=json`, `lang=ru_RU`, `results=1`. URI отправляется отдельным параметром
`uri`, без `geocode`; reverse отправляет `geocode=lon,lat`, `sco=longlat`.
Автотесты используют вымышленные ключи и сохранённые или фиктивные ответы через
MockTransport с запретом сетевых подключений. Они не расходуют лимит.

## Дорожная оценка Router API

`POST /api/v1/road-route?dummy=true` принимает:

```json
{"points":[{"lat":60.002,"lon":30.296},{"lat":60.036,"lon":30.445}],"traffic_mode":"on","departure_at":null}
```

`points` содержит строго две точки. `traffic_mode` — `on` (по умолчанию) или
`off`; `departure_at` необязателен. В реальном режиме с пробками дата должна
быть будущей и иметь часовой пояс. Если её нет, Яндекс выбирает текущее время.
В режиме `off` дата игнорируется и в ответе `departure_at=null`.

Ответ содержит `mode`, `traffic_mode`, `traffic_type`, `departure_at`,
`calculated_at`, `route` и `warnings`. Внутри `route`: `distance_meters`,
`duration_seconds` и GeoJSON `geometry`. Длительность сохраняет дробные секунды
провайдера, без округления каждого шага. Общая линия соединяет шаги по порядку,
не дублируя общие концы; некорректная или разорванная линия отклоняется.
`traffic_type` Яндекса — `realtime`, `forecast` или `disabled`;
в dummy это null. `FAIL` любого участка даёт HTTP 200 с `route=null` и
предупреждением; неполный маршрут не возвращается как успешный.

Это оценка автомобиля, не время автобуса и не результат OTP. Не заменять
ей напрямую время ОТ: сначала нужно сопоставить траектории и согласовать
поправку с учётом остановок и выделенных полос. Сравнение `on` и `off` требует
двух явных вызовов и может дать разные дорожные маршруты; разницу длительностей
нельзя автоматически трактовать как задержку на одной и той же траектории.

Реальный запрос следует
[формату Router API](https://yandex.ru/maps-api/docs/router-api/request.html):
`https://api.routing.yandex.net/v2/route`, `mode=driving`,
`waypoints=lat1,lon1|lat2,lon2`. Для `off` передаётся `traffic=disabled`,
для `on` параметр `traffic` опускается. Будущее время переводится в UNIX-секунды
с округлением вверх, чтобы не отправить время раньше указанного пользователем.
`results`, оптимизация порядка точек и дополнительные платные опции не запрашиваются.
В [ответе](https://yandex.ru/maps-api/docs/router-api/response.html) читаются
`route.legs[].steps[]`: суммируются `length` и `duration`, линии из `[lat,lon]`
превращаются в `[lon,lat]`. Устаревающий `waiting_duration` отдельно не добавляется.

Ключ — `YANDEX_ROUTER_API_KEY`, в k3s из Secret `yandex-api`, ключ `router`.
Отсутствие ключа: 503 `router_provider_unavailable`; квота: 503
`router_provider_quota`; таймаут: 504 `router_provider_timeout`; остальные
ошибки HTTP или некорректный ответ: 502 `router_provider_error`.
Один вызов — максимум один запрос Яндексу, без повторов и редиректов.
HTTPX-логи маскируют query-параметр `apikey` даже на уровне INFO.
Dummy использует прямую линию и фиксированную скорость, не имитирует настоящие
пробки; его результаты явно помечены и не расходуют запросы.

Оба набора адаптеров можно тестировать независимо от OTP. `POST /api/v1/routes`
в режиме `otp` обращается к планировщику; без него отвечает ошибкой
недоступности. Дорожная оценка не выдаётся вместо реального маршрута
общественного транспорта.

## Маршрут общественного транспорта

Запрос маршрута:

```json
{"points":[{"lat":60.002,"lon":30.296},{"lat":60.036,"lon":30.445}],"passenger":{"ticket_profile":"podorozhnik_wallet"},"departure_at":"2026-11-10T15:00:00+03:00","traffic_mode":"off","max_results":5}
```

`points` — упорядоченный массив точек маршрута: сейчас принимаются **строго две** (A и B). Ноль, одна, три и более точки, а также старый запрос с `from`/`to` дают HTTP 422. Промежуточные точки пока не поддерживаются. Поля `from`/`to` в ответе для концов отдельного сегмента сохраняются.

`passenger` содержит `ticket_profile`: `podorozhnik_wallet`, `unlimited_surface`,
`unlimited_metro`, `unlimited_all`, `bank_card`. По умолчанию — `bank_card`.
`uncovered_payment=bank_card|podorozhnik_wallet` настраивает оплату вне покрытия
безлимитного проездного. Метаданные профилей доступны через ticket-profiles;
расчёт стоимости пока не реализован. Полный городской безлимит не означает
автоматического покрытия электричек или областных маршрутов.

Подорожник: пересадочная цепочка наземного городского транспорта 60 минут
от первой валидации, не скользящее окно. В 2026 году первая посадка 65 ₽,
вторая 14 ₽, следующие 0 ₽. Оплата метро прекращает цепочку. Источник:
https://orgp.spb.ru/проездные/ . Банковский профиль не применяет скидки ЕКП/Мир.

Номенклатура сверена основным агентом с [официальными видами проездных](https://orgp.spb.ru/проездные/) и [зонами действия](https://orgp.spb.ru/зона-действия/). Профиль **не рассчитывает цены, применимость и покрытие билетов** — API возвращает переданный профиль в `passenger` и предупреждение об этом. Реальные тарифы задаёт отдельный блок `fare` (см. раздел «Тарифы»), он не выводится из профиля. Ни нулевой цены, ни обещания бесплатного проезда dummy-ответ не выдаёт. Профили подготовлены как основа будущей тарификации и фильтров.

Будущий поиск принимает `providers` (default `["otp"]`), `modes` — массив
enum bus/tram/trolleybus/metro/rail, `exclude_modes`, `max_transfers`,
`walk_speed=slow|normal|fast`, `less_walking`. MVP — только OTP. Сам реальный
поиск пока не реализован. Демо учитывает разрешение автобуса и скорость ходьбы;
провайдеры, дорожные поправки, предпочтение меньше ходьбы и расчёт оплаты пока
остаются предпочтениями будущего реального планировщика.
Происхождение каждого варианта и использованные поправки описаны в OpenAPI
через `provenance`; это не обещание реализованной агрегации провайдеров.

Время обязательно с часовым поясом; длительности в целых секундах; координаты WGS84; GeoJSON использует порядок `[lon,lat]`. Ответ включает `mode`, `routes[].legs`, `gtfs_version`, `graph_version`, `calculated_at`, `warnings`. Сегменты содержат исходную длительность, источник длительности и геометрию. Синтетические IDs имеют префикс `dummy:`.

Для карточки и карты каждый маршрут содержит `name` (свободная подпись, без
фиксированного набора названий), `distance_meters`, `duration_seconds` и общую
`geometry` типа GeoJSON LineString. `legs` — последовательные участки того же
маршрута: ходьба, ожидание и поездки с отдельными временами и транспортом.
Геометрия участка остаётся в `legs[].geometry`; общая линия следует этим
участкам в порядке движения. Ожидание не добавляет расстояния или перемещения.
Координаты обеих геометрий типизированы как `[lon, lat]`, минимум две позиции.
В демо расстояние суммируется по геометриям сегментов: для автобуса используется
записанная GTFS-геометрия, пешие подходы изображаются прямыми линиями.
Фронт из ветки `front` отображает `distance_meters` как `distance`,
`duration_seconds` как `duration`, а долготу точки `lng` передаёт как `lon`.
Из ответа используется массив `routes`; метаданные и предупреждения остаются
в общем объекте ответа. Dummy нельзя показывать как реальный результат поиска.

Ошибка: `{"error":{"code":"planner_unavailable","message":"..."}}`, HTTP 503. Непригодная дата GTFS: `invalid_service_date`, HTTP 422. Ошибка входной схемы: стандартный FastAPI HTTP 422 с `detail`. Корректный ответ планировщика без вариантов — HTTP 200 с `mode=real`, `routes=[]`; это отличается от недоступности сервиса.

## Маршрутизация через OTP

`PLANNER_MODE=otp` включает адаптер `app/otp.py`. Адрес сервиса — `OTP_URL`
(по умолчанию `http://localhost:8080`), таймаут — `OTP_TIMEOUT_SECONDS`
(по умолчанию 20). Один запрос маршрута — ровно один HTTP-вызов GraphQL
`POST /otp/gtfs/v1`, без повторов и редиректов.

Запрашиваются только режимы, которые есть в публичном контракте: подход и отход
пешком, пересадка пешком, транспорт `BUS`, `TRAM`, `TROLLEYBUS`, `SUBWAY`, `RAIL`.
Велосипед, автомобиль, такси и самокаты не запрашиваются, поэтому в ответе их нет.

Маппинг OTP → контракт:

| OTP | Ответ API |
|---|---|
| `Itinerary.start`/`end`/`duration` | `Route.start_at`/`end_at`/`duration_seconds` |
| `numberOfTransfers` | `Route.transfers` |
| `legs[].distance` | сумма в `Route.distance_meters` |
| `WALK`, `BUS`, `TRAM`, `TROLLEYBUS`, `SUBWAY`, `RAIL` | `Leg.mode` = `walk`, `bus`, `tram`, `trolleybus`, `metro`, `rail` |
| `legGeometry.points` | `Leg.geometry` (encoded polyline, точность 5) |
| `route.gtfsId`, `trip.gtfsId` | `Leg.line.route_id`, `Leg.line.trip_id` |
| `from.stop.gtfsId`, `to.stop.gtfsId` | `Place.stop_id` |
| `start.scheduledTime` / `estimated.time` | `Leg.start_at` |

Правила и ограничения:

- `estimated` имеет приоритет над `scheduledTime`. Сейчас OTP работает без
  GTFS-RT, поэтому используется расписание. `duration_source` у всех легсов —
  `schedule`.
- OTP не отдаёт отдельный сегмент ожидания. Backend синтезирует `mode="wait"`
  между соседними легсами, если между прибытием и отправлением есть разрыв.
  Геометрия такого легса — две одинаковые точки, расстояние не добавляется.
  Благодаря этому сумма длительностей легсов сходится с длительностью маршрута.
- `Route.id` и `Route.name` формирует backend: OTP не даёт готового названия
  варианта. Название собирается из видов транспорта и номеров маршрутов
  (`Автобус 24 → Автобус 100`), для пешеходного варианта — `Пешеходный маршрут`.
- Полная `Route.geometry` собирается из геометрий легсов в порядке движения,
  общие концы не дублируются.
- `passenger.ticket_profile` на планирование не влияет: возвращается как есть
  с предупреждением. Реальные тарифы задаёт `fare` — см. следующий раздел.
- `traffic_mode=on` не применяется к общественному транспорту: OTP использует
  расписание. В ответ добавляется предупреждение. Дорожная оценка остаётся
  отдельной ручкой `POST /api/v1/road-route`.
- `routingErrors` не прерывают ответ: каждый код попадает в `warnings`.
  `OUTSIDE_SERVICE_PERIOD` означает дату вне расписания, и OTP может вернуть
  только пеший вариант. Такой ответ сейчас отдаётся как есть с двумя
  предупреждениями (`OUTSIDE_SERVICE_PERIOD` и «only walking options»).
  Замена на HTTP 422 `invalid_service_date` обсуждалась и отложена.
- Ошибки: HTTP 502 `planner_error` (не-200 от OTP, GraphQL `errors`,
  неожиданная структура), 503 `planner_unavailable` (сеть, отказ соединения),
  504 `planner_timeout`. Dummy-ответ при ошибке реального режима не подставляется.

## Тарифы (`fare`)

`POST /api/v1/routes` принимает необязательный блок `fare`. Без него поиск
идёт только по времени (поведение прежнее), и `Route.fare` в ответе — `null`.

```json
{"points":[...],"departure_at":"2026-11-11T12:00:00+03:00",
 "fare":{"rules":[{"mode":"metro","cost_rub":0},{"mode":"bus","cost_rub":65}],
         "transfer_cost_rub":20,"value_of_time_rub_per_hour":600}}
```

| Поле | Смысл |
|---|---|
| `rules[].mode` | `bus`, `tram`, `trolleybus`, `metro`, `rail`; не более одного правила на вид, иначе 422 |
| `rules[].cost_rub` | цена одной посадки в этот вид; `0` — бесплатно |
| `transfer_cost_rub` | надбавка за каждую пересадку (по умолчанию `0`) |
| `value_of_time_rub_per_hour` | сколько рублей стоит час в пути; переводит тарифы в стоимость поиска (по умолчанию `600`) |

Виды без правила считаются бесплатными: в поиск идёт `reluctance=1.0`, а в
стоимости маршрута они участвуют с нулём и попадают в `warnings`
(`No fare rule for mode(s) ...`).

**Как это попадает в OTP.** GraphQL `planConnection` принимает на каждый вид
транспорта только множитель времени — `modes.transit.transit[].cost.reluctance`,
и аддитивной цены поездки в OTP 2.11 нет. Поэтому тариф пересчитывается в
секунды обобщённой стоимости через `value_of_time_rub_per_hour` и делится на
типовую длительность поездки (900 с):

```
reluctance = 1 + (cost_rub · 3600 / value_of_time) / 900,    не более 20
```

Проверено на живом OTP для пары «Сенная — Василеостровская»: при
`BUS reluctance=1.0` лидирует связка автобусов, при `×5` появляется пеший
вариант и связка «автобус + трамвай», при `×20` автобус исчезает из выдачи
полностью. Метро с `cost_rub=0` остаётся нейтральным (`1.0`) и потому
предпочтительнее платного автобуса.

**Что важно понимать.** Множитель влияет на *ранжирование*, а не даёт точную
цену: `Route.fare` считается отдельно — по факту легсов ответа
(одна плата за посадку, `transfers` между транспортными легсами умножаются на
`transfer_cost_rub`). OTP не гарантированно находит вариант с минимальной
`fare.amount_rub` — он оптимизирует обобщённую стоимость; об этом говорит
предупреждение `time multipliers`. Ответ содержит `currency`, `amount_rub`,
`items[]` (`mode`, `rides`, `cost_rub`), `transfers` и `transfer_cost_rub`.

В режиме dummy блок `fare` принимается, но не применяется: синтетический
маршрут возвращает `fare=null` и предупреждение `Fare rules are ignored`.

`GET /api/v1/data/status` читает `otp/current.json` и `otp/build-status.json`
и отдаёт их как `graph` и `graph_check`; `graph_version` — это `version` графа.
Статус переходит в `degraded` и добавляет предупреждения, если граф собран из
другой версии GTFS (`gtfs_source_sha256` не совпадает с текущим `sha256`),
не подтверждён загрузкой (`activated_at` пуст), его период обслуживания истёк
или последняя сборка завершилась ошибкой.

`PLANNER_MODE=dummy` — демонстрационный режим без OTP и без Яндекса;
`unavailable` — реальный режим без планировщика, отвечает 503.
Реальные вызовы требуют явного `?dummy=false` в любом режиме.

`DATA_ROOT=/data`: API читает самодостаточный `gtfs/current.json` с `sha256` и метаданными текущей загрузки/проверки календаря. В ответе `manifest` содержит этот же снимок. Каталоги старых версий могут удаляться сразу после публикации, поэтому status endpoint не читает файлы по пути `versions/<sha256>` и не зависит от истории GTFS. Каждый ответ связывает SHA и календарные метаданные из одного атомарно прочитанного документа; следующий запрос может уже видеть новый документ. `gtfs/refresh-status.json` содержит последний результат обновления. Граф: `otp/current.json` с полем `version` и `otp/build-status.json`. API не записывает эти файлы и не обновляет GTFS в HTTP-запросах. `active_service_ids=0` относится только к `service_date` текущей проверки, а не ко всем датам; окончательную проверку произвольной даты выполняет OTP и возвращает `OUTSIDE_SERVICE_PERIOD`.

Контейнер собирается из корня репозитория: `docker build -f backend/Dockerfile .`; базовый Python поддерживает amd64/arm64. Переменная `PLANNER_MODE=dummy` нужна явно для демонстрационной выкладки.

Для фронтенда на другом origin укажите `CORS_ORIGINS=http://localhost:5173,https://frontend.example`; по умолчанию cross-origin доступ не включён. API не требует ключей для публичных read-only/demo endpoints.


## GTFS и выбор геосервиса

suggest, geocode, reverse и road-route принимают `provider=yandex|2gis`
(default yandex), независимо от `dummy=true`. Ответ содержит выбранный provider;
при отказе одного провайдера другой автоматически не вызывается. 2ГИС использует
`DGIS_API_KEY` из Secret dgis-api/apikey. Для выбранного `dgis:<id>` нужен доступ
ключа к Places API; для Yandex сохраняется ymapsbm1 URI. Токены нельзя смешивать.

Реальные справочные ручки читают архив `DATA_ROOT/gtfs/versions/<sha>/feed.zip`:
- GET /api/v1/stops?bbox=minLon,minLat,maxLon,maxLat
- GET /api/v1/stops/{stop_id}
- GET /api/v1/stops/{stop_id}/departures?departure_at=ISO8601
- GET /api/v1/transit-routes
- GET /api/v1/transit-routes/{route_id}
- GET /api/v1/trips/{trip_id}

`dummy=false` читает локальный снимок, не обновляет его и не вызывает внешние API.
Списки поддерживают limit/offset; q/modes — где предусмотрено OpenAPI.
Календарь проверяется для отправлений. Интервальные рейсы exact_times=0 возвращают
schedule_type=frequency, headway_seconds и окно движения, без точного времени
посадки. GTFS-времена >=24:00:00 и исключения календаря учитываются.
Большие таблицы читаются потоково; одновременно обслуживаются максимум два
GTFS-запроса для ограничения памяти. На полном архиве smoke peakRSS около240МБ.

Демо основано на общем небольшом demo.zip: линия 193, реальные остановки и два
шаблона рейса; календарь и 10-минутное расписание явно синтетические. С ним согласованы
подсказки, маршруты, карточки остановок и машины.
GET /api/v1/vehicles с dummy=false возвращает503 realtime_unavailable:
GTFS-RT ещё не подключён. Dummy-позиции имеют фиксированное время и stale.

11 ноября также проверены четыре реальные ручки 2ГИС: suggest, geocode по тексту,
reverse, road-route — все HTTP200, ровно4 обращения. Ответы без ключа:
`app/fixtures/dgis/live-example-2026-11-11.json`. Они воспроизводятся офлайн в
регрессионных тестах. ID→Places lookup отдельно живым вызовом не проверялся.


### Метаданные ответа `/routes`

`mode=dummy` обозначает демонстрационные данные, `mode=real` — результат планировщика.
`real` не обещает учёт пробок или наличие realtime: это видно из `sources`.
Сейчас реализован только dummy-ответ; `dummy=false` по-прежнему возвращает ошибку
недоступности планировщика. Новые модели не включают реальные обращения к провайдерам.

`sources.candidate_providers` перечисляет фактически использованные планировщики,
`sources.traffic_providers` — фактически применённые дорожные поправки,
`sources.realtime` — `gtfs_rt`, `unavailable` или `dummy`. Для каждого варианта
`provenance` сохраняет его собственные источники. В dummy списки пустые независимо
от выбранных в запросе провайдеров.

Каждый `leg` содержит `distance_meters`; сумма равна расстоянию маршрута. Для
ожидания расстояние равно нулю. `duration_source` поддерживает `dummy`, `schedule`,
`yandex`, `2gis`, `estimated`. Опциональный `metro_wait_estimate` описывает
моделируемое ожидание метро и допустим только у `mode=wait` с
`duration_source=estimated`. Он хранит диапазон интервалов, выбранный модельный
интервал, его половину как оценку ожидания и происхождение данных. Демо-маршрут
с автобусом возвращает это поле как `null`; расчёт метро ещё не подключён.


### Реализованные пути Яндекса и 2ГИС

Все четыре ручки работают с `provider=yandex` и `provider=2gis`:

| Ручка | Реальная операция при `dummy=false` |
|---|---|
| `GET /api/v1/suggest?q=...` | Подсказки выбранного провайдера |
| `GET /api/v1/geocode?q=...` | Адрес → координаты |
| `GET /api/v1/geocode?uri=...` | Выбранная подсказка → координаты |
| `GET /api/v1/reverse?lat=...&lon=...` | Координаты → адрес |
| `POST /api/v1/road-route` | Автомобильный маршрут с геометрией, расстоянием и временем |

В `geocode` задаётся ровно одно из `q` и `uri`. URI Яндекса передаётся геокодеру
как есть; `dgis:<id>` разрешается одним запросом Places API `/items/byid`.
Разрешение URI 2ГИС требует доступа ключа к Places API, независимо от наличия
доступа к геокодеру. Между провайдерами нет автоматических переключений.

По умолчанию остаётся `dummy=true`. В реальном режиме каждая операция делает
не больше одного внешнего запроса; повторов при ошибках нет. HTTP 408/504 и
сетевой таймаут дают наш HTTP 504, исчерпание квоты HTTP 429 — наш HTTP 503,
прочие некорректные ответы — HTTP 502. Ошибки не подменяются dummy-результатом.

Полный HTTP-путь для обоих провайдеров, включая оба варианта геокодирования,
проверяется на сохранённых реальных ответах и моках в `tests/test_geo_provider_paths.py`.
Тесты блокируют сетевые соединения и не расходуют квоты. Главная `POST /api/v1/routes`
остаётся отдельно: реальный поиск общественного транспорта этим изменением не включается.
