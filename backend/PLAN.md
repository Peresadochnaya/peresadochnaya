# План интеграции маршрутизации

Обновлено 11 ноября 2026 года. Цель ближайшего этапа — получать варианты
общественного транспорта из OTP, оценивать дорожные участки через Яндекс
и возвращать фронтенду согласованные времена, пересадки и геометрию.

## Уже подготовлено

- FastAPI, CI/CD, HTTPS и health endpoints работают в k3s.
- GTFS проверяется каждые 20 минут через авторизованный HTTP-прокси arctur
  по NetBird. Хранится только свежая версия.
- Контракт принимает массив `points` строго из двух точек. Маршрут содержит
  свободное `name`, `distance_meters`, `duration_seconds`, общую GeoJSON
  `geometry` и подробные `legs` с отдельными геометриями и временами.
- Реализованы и выложены suggest, geocode, reverse и Router API; CI/CD успешен.
- Router API доступен отдельно через `POST /api/v1/road-route`.
  Строго две точки, один режим трафика на вызов, `dummy=true` по умолчанию.
  Кандидаты ОТ и пересадки пока не пересчитываются.
- Адресные и дорожные адаптеры проверяются через MockTransport с запретом
  сетевых подключений. 11 ноября выполнено по одному живому вызову suggest,
  geocode, reverse и road-route, все HTTP 200. Расход: Suggest 1, Geocoder 2,
  Router 1. Сырые ответы без ключей и нормализованные данные сохранены в
  `app/fixtures/yandex/live-2026-11-11.json`; добавлено их воспроизведение в dummy.
  Изменения dummy пока не выложены.
- Ключи геокодера, саджеста и Router API сохранены отдельно в Kubernetes
  Secret. Ключ матрицы расстояний не используется.

## Ограничения

- На всех ручках с потенциальным обращением к Яндексу query-параметр
  `dummy=true` по умолчанию. Реальный режим включается только явным
  `dummy=false`; флажок на фронте управляет этим параметром.
- Dummy-ответы явно помечаются; при ошибке реального режима нельзя подменять
  результат синтетическим маршрутом.
- Лимит Яндекса очень мал: Router — 100 запросов, геокодер и саджест — по 1000.
  Разрешённая проверка 11 ноября использовала 4 обращения; дополнительных
  запросов для исправления ошибок не потребовалось. До отдельной
  договорённости не выполнять живые запросы, включая smoke tests и проверки
  ключей. Тесты и CI используют только фиктивные ответы.
- Не делать автоматических повторов, редиректов и фоновых запросов к Яндексу.
  Suggest на фронте требует debounce и отмены устаревших результатов.
- Не хранить ключи в Git, OpenAPI, примерах, логах или ответах фронту.
- Любой коммит требует отдельного аппрува пользователя. Перед ним сообщить
  состав изменений и название. Публикация изменений — в ветку пользователя.
- Не менять существующие скрипты Серафима без согласования. OTP и сборку графа
  ведёт Динар; алгоритмические подходы — Фёдор; фронтенд — Егор.

## 1. Адаптер Яндекс Router API

Реализован независимо от OTP: нормализация автомобильной оценки, ошибки,
проверка будущего времени, преобразование координат, dummy и тесты.
Для последующей интеграции остаются сопоставление траектории ОТ с дорожной
линией и решение о промежуточных точках: публичный контракт пока строго A/B.

1. Изучить актуальную документацию запросов и ответов Router API.
2. Определить внутренний контракт оценки дорожного участка: координаты и
   промежуточные точки, направление, момент въезда, геометрия, время с пробками
   и без них, источник и время расчёта.
3. Составить запросы по документации. Проверить, какие значения доступны
   одним ответом, а где потребуются отдельные обращения. Не обещать две оценки
   ценой одного запроса без подтверждения формата API.
4. Реализовать dummy и настоящий адаптер с ограниченным таймаутом,
   диагностируемыми ошибками и без повторов. Не создавать публичную ручку,
   расходующую квоту, без необходимости: адаптер может вызываться внутри routes.
5. Проверить запросы и разбор ответов через MockTransport, в том числе
   координатный порядок, отсутствие маршрута, квоту, таймаут и повреждённый ответ.

Документация: https://yandex.ru/maps-api/docs/router-api/index.html

## MVP поиска

Только OTP, без Яндекс/2ГИС-поправок и без realtime. Реальный /routes пока не реализовывать.
Предпочтения: массив modes, walk_speed enum, less_walking; пять ticket_profile и
настраиваемый uncovered_payment. Будущая агрегация сохраняет provenance каждого кандидата.

## 2. Интеграция OTP

1. Получить у Динара рабочий адрес OTP, версию, формат API и пример маршрута.
2. Согласовать доступность GTFS/OSM, версию графа и календарь обслуживания.
   Текущая выгрузка GTFS ранее не содержала действующих service_id на дату
   проверки; причину и допустимое решение нужно выяснить, а не скрывать ошибку.
3. Привести ответ OTP к нашим `Route` и `Leg`, сохранив идентификаторы рейсов,
   остановки, расписание и геометрию.
4. Для MVP получать несколько групп кандидатов: все виды транспорта,
   метро с трамваем, автобус с троллейбусом; ходьба нужна для подходов и пересадок.
   Конкретные режимы уточнить по возможностям настроенного OTP.
5. Удалять дубликаты кандидатов до обращения к Яндексу.

## 3. Пересчёт времени и пересадок

1. Выбирать дорожные участки, для которых применима оценка автомобильного
   трафика. Метро не корректировать автомобильными пробками; трамвай требует
   отдельного решения с учётом выделенного полотна.
2. Не приравнивать время автомобиля ко времени автобуса: учитывать остановки,
   посадку и различия траекторий. Способ применения поправки согласовать
   с Фёдором и явно отмечать ограничения оценки.
3. Сохранить исходные времена, исправленные времена и источник поправки.
4. Пересчитывать маршрут последовательно. Задержка участка меняет момент
   прибытия на пересадку, ожидание и доступность следующего рейса.
5. Если пересадка пропущена, найти следующий допустимый рейс или запросить
   перепланирование. Нельзя просто сдвинуть расписание следующего транспорта.
6. Повторно ранжировать только согласованные по времени варианты и вернуть
   лучший маршрут с альтернативами. Итоговая длительность должна включать
   ходьбу, ожидания и поездки.
7. GTFS-RT Vehicle Positions использовать как отдельный источник наблюдений.
   Наличие позиций само по себе не даёт готовых TripUpdates или времени прибытия.

Для MVP используем постобработку кандидатов планировщика. Генерация собственных
GTFS-RT TripUpdates и периодическая пересборка GTFS с пробками — следующие
варианты развития, не обязательная часть ближайшего этапа.

## 4. Фронтенд и билеты

- Основа интерфейса — ветка `front`: точки A/B, выбор варианта и общая линия.
  Фронт сопоставляет `lng` с `lon`, `distance` с `distance_meters`, `duration`
  с `duration_seconds` и использует массив `routes` из ответа.
- Для адресов: suggest → выбор `uri` → geocode. Для точки на карте: reverse
  меняет подпись, но сохраняет исходную точку клика для маршрутизации.
- Не закреплять названия «Быстрый / Короткий / Живописный» как категории API.
- Сохранить профили петербургских проездных. Правила покрытия и платных
  пересадок требуют отдельной реализации; пока не обещать бесплатный проезд
  или рассчитанную стоимость.
- Слой остановок и расписание в карточке остановки — последующий контракт;
  не считать их уже реализованными адресным поиском.

## 5. Проверки перед публикацией

- Тесты адресных адаптеров и Router API без сети и настоящих ключей.
- Тесты OTP adapter, дедупликации, перестановки вариантов после поправки,
  пропущенной пересадки, ожидания, полуночи и рейсов GTFS после 24:00.
- Проверка временной непрерывности, единиц расстояния/времени и геометрии.
- Корневой `openapi.yaml` совпадает со схемой FastAPI; YAML манифестов рендерится.
- Дополнительный живой тест Яндекса выполняется только по отдельной
  договорённости, с заранее известным количеством вызовов. Четыре сохранённых
  успешных случая подтверждают проверенные сценарии, но не все комбинации API.
- Показать пользователю diff и результаты тестов, получить аппрув коммита.
