# План интеграции маршрутизации

## Статус реализации — 12 ноября 2026 года

Реализован конвейер дорожной коррекции OTP по [одобренной спецификации](../docs/superpowers/specs/2026-11-12-traffic-correction-design.md).
[Матрица проверок](../docs/superpowers/specs/2026-11-12-traffic-correction-tests.md)
содержит проверяемые сценарии и ограничения точности. Итоговая проверка:
509 backend + 103 прочих Python + 14 frontend = **626 пройденных тестов**.
Последняя полная backend-проверка: 509 passed за 10,60 с, одно предупреждение;
это на 177 тестов больше исходной базы 332. OpenAPI snapshot совпадает,
`git diff --check` чистый. Прочие 103 Python-теста, 14 frontend-тестов и frontend build
успешно проверены ранее; соответствующие компоненты не менялись.

Дополнительно заполнен и проверен направленный слой полос: **674 пары остановок,
1699 геометрических вариантов**, 433 OSM-представления и 6 официальных фрагментов
Малой Морской. Один официальный участок разрешён по точным границам; остальные
36 записей остаются неполностью привязанными. [Подробный отчёт](../research/traffic-correction/bus-lanes/live-report.md)
содержит ровно три выполненных платных поиска Яндекса (0 запросов 2ГИС),
исходные ответы и строгие офлайн replay. Исправлены точные повторы после
восстановления хвоста и зависимость выбранной поездки от порядка загрузки
чужих геометрий; сетевой бюджет трёх поисков исчерпан.

Для реального поиска: `POST /api/v1/routes?dummy=false`, в JSON запроса
`"traffic_mode": "on"` вместе с обычными points/departure_at. Без этого флага
остаётся исходный расчёт OTP; dummy не обращается к платным провайдерам.
На поиск допускается до одного автомобильного расчёта 2ГИС с альтернативами
и одного Яндекс-запроса, без платных повторов. Свежесть наблюдений — 30 минут
от получения без продления чтением; общий дедлайн — 15 секунд.

Конвейер читает существующий дисковый GTFS-индекс из MR23 и версии источников
активного графа OTP. Исходники работающего графа сохраняются при обновлении
latest; несовместимая база не подменяется новой, а даёт неполную оценку.
Поправка положительная, относится к движению между остановками и не добавляет
известную стоянку повторно. Задержанные интервальные пересадки перепланируются;
невосстановимая недостижимая посадка исключается с исходным вариантом в debug.

Необязательный файл `/data/traffic-road-status.json` задаёт проверенные сведения
о направленных рёбрах. Пример формата (условные ID и источник):

```json
{"version":"2026-11-12","edges":[{"feed_id":"gtfs","from_stop_id":"a","to_stop_id":"b","status":"dedicated","source":"https://example.test/evidence","date":"2026-11-12","spans":[{"start_m":0,"end_m":100}]}]}
```

Допустимые status: `dedicated`, `segregated`, `shared`, `unknown`. Обязательны
версия файла, источник и дата записи. Без spans статус относится ко всему ребру;
со spans — только к указанным непересекающимся диапазонам метров вдоль его
направленной геометрии. Диапазон наследует status/source/date записи и может
переопределить их; остальная часть остаётся unknown. При отсутствии сведений
поправка разрешена с явным предупреждением о неизвестном статусе полосы.
Официальный текстовый перечень сам по себе не превращается в готовый геослой.

Ниже сохранены исходный план и исследовательские договорённости. Формулировки
о будущей реализации читаются как история этапа; текущий контракт определяется
спецификацией и статусом выше.

## Согласованные решения: автомобильные оценки и кэш

Зафиксировано по обсуждению 12 ноября 2026 года. Это план следующего этапа,
а не описание уже реализованной интеграции. Пока только планирование.

### Источники и бюджет

- OTP остаётся источником вариантов маршрутов общественного транспорта.
  Автомобильные маршруты внешних провайдеров дают геометрию и оценки времени
  для сопоставления, а не новые допустимые маршруты автобусов.
- 2ГИС: один автомобильный расчёт A → B с альтернативами, текущими пробками
  (`transport=driving`, `route_mode=fastest`, `traffic_mode=jam`,
  `output=detailed`). Не задавать `utc` для этого сценария; не переключаться
  на статистический прогноз. `alternative` задаёт число дополнительных
  вариантов сверх основного; точное значение выберем при реализации.
- Яндекс: один автомобильный запрос для получения текущих оценок на нужных
  дорожных участках и расширения покрытия кэша, до 50 точек в запросе.
  Это лимит точек, не число запросов. Не задавать будущее `departure_time`;
  проверять фактический `traffic_type` ответа, прогноз не выдавать за realtime.
- На один поиск допустимы до 1 запроса Яндекса + 1 автомобильного расчёта
  2ГИС. Это верхняя граница: при достаточном свежем покрытии кэша обращения
  пропускаются. Автоматические повторы и дополнительные платные вызовы
  для заполнения пробелов в этот бюджет не входят.
- В 2ГИС альтернативы одного набора точек не оплачиваются дополнительно,
  но независимые пары внутри пакета тарифицируются каждая отдельно.
  Такой пакет не считать одним расчётом для ограничения расхода.
- Текущие договорённости о бюджете описывают будущую работу приложения.
  Платные проверочные вызовы при разработке по-прежнему согласуются отдельно.

### Расширение покрытия

1. Сначала данные для наземных участков текущих кандидатов OTP.
2. Дополнительные точки Яндекса — для полезных дорог района, ещё не покрытых
   свежим кэшем. Свежие участки повторно не запрашивать без необходимости.
3. Польза измеряется новыми покрытыми участками ОТ на оплаченный расчёт,
   а не заполнением всех 50 мест любой ценой.
4. Цепочка A → B → C → D — единый маршрут через точки, а не независимый
   пакет. Влияние дополнительных точек на альтернативы A → B проверить.
   Сочетание 3+ waypoints и results в Яндексе на нашем ключе пока не проверено;
   в документации явного запрета нет. Это проверяемое предположение.
5. У 2ГИС до 10 точек суммарно, включая до 8 промежуточных `type=pref`.
   Лимит 50 точек Яндекса на 2ГИС не переносить.

### Обязательный кэш

- TTL свежих дорожных оценок — **1800 секунд (30 минут)**; последняя договорённость заменяет прежние 15 минут.
- 30 минут действуют для дорожных наблюдений; `dummy=true` по-прежнему
  не вызывает провайдеров, реальные и синтетические данные не смешиваются.
- Кэш должен переиспользоваться между поисками с разными A/B, если они
  проходят по одним направленным дорожным участкам; одного ключа A/B мало.
- Хранить производные оценки/коэффициенты, источник, направление,
  время получения и необходимые данные привязки к участку. Не использовать
  весь сырой ответ провайдера как основной кэш маршрута.
- Точное представление значения кэша и его базу сравнения согласовать вместе
  с алгоритмом. Отношение автомобильного времени к расписанию конкретного
  автобуса нельзя молча считать универсальным коэффициентом улицы.
- Свежесть считать от момента получения оценки, не продлевать чтениями.
  Объединять одновременные обращения за теми же данными, чтобы не тратить
  квоту несколько раз.
- Оценки Яндекса и 2ГИС на совпадающей дороге не складывать и не умножать
  последовательно: выбирать одну по согласованному правилу свежести/качества.
  Отсутствие покрытия или истечение TTL не означает отсутствие пробки.

### Подготовка данных и границы ближайшей работы

- Текущие адаптеры возвращают общую длительность и геометрию; для алгоритма
  нужно сохранять внутреннюю детализацию всех автомобильных альтернатив.
- Яндекс: `routes[].legs[].steps[]` при results, либо `route.legs[].steps[]`.
  Сохранять duration, length и polyline каждого шага.
- 2ГИС: `result[].maneuvers[].outcoming_path` — duration, distance, geometry.
  Duration относится ко всему outcoming_path, не к каждому элементу geometry;
  у конечного манёвра outcoming_path может отсутствовать.
- Не требуется получать автомобильное время без пробок вторым вызовом:
  модель сравнения с OTP будет обсуждаться отдельно. Не называть разницу
  «чистой задержкой из-за пробки» без соответствующей базы сравнения.
- Сначала подготовить адаптеры, внутренний формат данных, кэш и контроль
  расхода. Затем отдельно обсудить геометрическое сопоставление, применение
  только положительной поправки, выделенные полосы и перерасчёт пересадок.
  Эти алгоритмы этим планом не утверждены и пока не реализуются.
- Проверки: несколько альтернатив, единицы и порядок координат, отсутствие
  последнего outcoming_path, частичное покрытие, противоположное направление,
  TTL, совместные обращения, квота, ошибки провайдера и отсутствие двойной
  поправки. Основные тесты используют сохранённые/синтетические ответы.

### Отложенный черновик: общественный транспорт 2ГИС

Запросы к API общественного транспорта 2ГИС **не делаем** на ближайшем этапе.
Ранее рассматривался отдельный запрос ОТ вместе с автомобильным, но итоговое
решение — только автомобильный. По наблюдению пользователя, в предыдущих
тестах учёт пробок в маршрутах ОТ 2ГИС был неудовлетворительным; это наблюдение
тех тестов, а не доказанное свойство любого ответа сервиса.

Генерация новых маршрутов ОТ, которых нет среди кандидатов OTP, отложена
на неопределённый срок. Возвращаться к этому после оценки существующих
кандидатов и качества сопоставления.

## Ограничения

- На всех ручках с потенциальным обращением к Яндексу query-параметр
  `dummy=true` по умолчанию. Реальный режим включается только явным
  `dummy=false`; флажок на фронте управляет этим параметром.
- Dummy-ответы явно помечаются; при ошибке реального режима нельзя подменять
  результат синтетическим маршрутом.
- Лимит Яндекса очень мал: Router — 100 запросов, геокодер и саджест — по 1000.
  Разрешённая проверка 11 ноября использовала 4 обращения; дополнительных
  запросов для исправления ошибок не потребовалось. До отдельной
  договорённости не выполнять живые запросы, включая smoke tests и проверки
  ключей. Тесты и CI используют только фиктивные ответы.
- Не делать автоматических повторов, редиректов и фоновых запросов к Яндексу.
  Suggest на фронте требует debounce и отмены устаревших результатов.
- Не хранить ключи в Git, OpenAPI, примерах, логах или ответах фронту.
- Любой коммит требует отдельного аппрува пользователя. Перед ним сообщить
  состав изменений и название. Публикация изменений — в ветку пользователя.
- Не менять существующие скрипты Серафима без согласования. OTP и сборку графа
  ведёт Динар; алгоритмические подходы — Фёдор; фронтенд — Егор.

## 1. Адаптер Яндекс Router API

Реализован независимо от OTP: нормализация автомобильной оценки, ошибки,
проверка будущего времени, преобразование координат, dummy и тесты.
Дорожное сопоставление и внутренние цепочки промежуточных точек реализованы
в конвейере routes. Публичный отдельный автомобильный контракт остаётся A/B.

1. Изучить актуальную документацию запросов и ответов Router API.
2. Определить внутренний контракт оценки дорожного участка: координаты и
   промежуточные точки, направление, момент въезда, геометрия, время с пробками
   и без них, источник и время расчёта.
3. Составить запросы по документации. Проверить, какие значения доступны
   одним ответом, а где потребуются отдельные обращения. Не обещать две оценки
   ценой одного запроса без подтверждения формата API.
4. Реализовать dummy и настоящий адаптер с ограниченным таймаутом,
   диагностируемыми ошибками и без повторов. Не создавать публичную ручку,
   расходующую квоту, без необходимости: адаптер может вызываться внутри routes.
5. Проверить запросы и разбор ответов через MockTransport, в том числе
   координатный порядок, отсутствие маршрута, квоту, таймаут и повреждённый ответ.

Документация: https://yandex.ru/maps-api/docs/router-api/index.html

## MVP поиска

Только OTP, без Яндекс/2ГИС-поправок и без realtime. Реальный /routes подключён
через внутренний OTP; текущие ограничения перечислены в backend/README.md.
Предпочтения: массив modes, walk_speed enum, less_walking; пять ticket_profile и
настраиваемый uncovered_payment. Будущая агрегация сохраняет provenance каждого кандидата.

## 2. Интеграция OTP

Сделано 11 ноября 2026 года:

1. Получен рабочий локальный OTP 2.11.0-SNAPSHOT, GraphQL `/otp/gtfs/v1`.
2. Согласованы GTFS/OSM и версия графа: `otp/data/current.json` хранит оба SHA,
   версию OTP и диапазон обслуживания. Календарь GTFS исправляется в копии
   внутри `otp/staging`, исходный фид не меняется.
3. Ответ OTP приводится к `Route` и `Leg` в `app/otp.py`; сохраняются
   идентификаторы маршрута, рейса и остановок, расписание и геометрия.
4. Для MVP запрашиваются подход, отход и пересадка пешком плюс `BUS`, `TRAM`,
   `TROLLEYBUS`, `SUBWAY`, `RAIL`. Пешеходные варианты возвращаются как есть
   с предупреждением, если транзитных сегментов нет.
5. В OTP включён встроенный фильтр
   `removeItinerariesWithSameRoutesAndStops`: повторные отправления с теми же
   линиями и остановками убираются до ответа бэку; бэк не фильтрует их сам.

Осталось:

1. Решить, отдавать ли `OUTSIDE_SERVICE_PERIOD` как HTTP 422
   `invalid_service_date` вместо walk-only варианта с предупреждением.
   Сейчас отложено.
2. Автоматизировать пересборку графа после обновления источников. Сейчас
   GTFS и метро обновляются каждые 20 минут, а граф — вручную через
   `otp/scripts/rebuild-k3s.sh`; скрипт перезапускает OTP после успешной сборки.

В k3s развёрнуты API и приватный OTP Service. Образ OTP закреплён digest,
одинаковым для сборки и сервера. Адаптер сохраняет фильтры транспорта,
нормализует GTFS ID и явно отклоняет неподдерживаемые предпочтения.

## 3. Пересчёт времени и пересадок

Реализовано согласно одобренной спецификации; список ниже сохраняет исходную
постановку. GTFS-RT и собственная генерация маршрутов остаются за границами этапа.

1. Выбирать дорожные участки, для которых применима оценка автомобильного
   трафика. Метро не корректировать автомобильными пробками; трамвай требует
   отдельного решения с учётом выделенного полотна.
2. Не приравнивать время автомобиля ко времени автобуса: учитывать остановки,
   посадку и различия траекторий. Способ применения поправки согласовать
   с Фёдором и явно отмечать ограничения оценки.
3. Сохранить исходные времена, исправленные времена и источник поправки.
4. Пересчитывать маршрут последовательно. Задержка участка меняет момент
   прибытия на пересадку, ожидание и доступность следующего рейса.
5. Если пересадка пропущена, найти следующий допустимый рейс или запросить
   перепланирование. Нельзя просто сдвинуть расписание следующего транспорта.
6. Повторно ранжировать только согласованные по времени варианты и вернуть
   лучший маршрут с альтернативами. Итоговая длительность должна включать
   ходьбу, ожидания и поездки.
7. GTFS-RT Vehicle Positions использовать как отдельный источник наблюдений.
   Наличие позиций само по себе не даёт готовых TripUpdates или времени прибытия.

Для MVP используем постобработку кандидатов планировщика. Генерация собственных
GTFS-RT TripUpdates и периодическая пересборка GTFS с пробками — следующие
варианты развития, не обязательная часть ближайшего этапа.

## 4. Фронтенд и билеты

- Основа интерфейса — ветка `front`: точки A/B, выбор варианта и общая линия.
  Фронт сопоставляет `lng` с `lon`, `distance` с `distance_meters`, `duration`
  с `duration_seconds` и использует массив `routes` из ответа.
- Для адресов: suggest → выбор `uri` → geocode. Для точки на карте: reverse
  меняет подпись, но сохраняет исходную точку клика для маршрутизации.
- Не закреплять названия «Быстрый / Короткий / Живописный» как категории API.
- Сохранить профили петербургских проездных. Правила покрытия и платных
  пересадок требуют отдельной реализации; пока не обещать бесплатный проезд
  или рассчитанную стоимость.
- Слой остановок и расписание в карточке остановки — последующий контракт;
  не считать их уже реализованными адресным поиском.
