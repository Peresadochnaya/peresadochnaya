# Память вспомогательного графа остановок

**Да, сам граф остановок помещается в оперативную память.** На текущем GTFS
измеренный граф с общими компактными геометриями занимает около 36 MiB
Python-объектов. Это вспомогательный граф для покрытия и поправок, не полный
маршрутизирующий граф OTP.

[Исходные измерения](stop-graph-memory.json). Проверка проведена 12 ноября
2026 года в отдельном временном Python-процессе на хосте k3s, вне контейнеров
API и OTP. Доступ к данным только для чтения, лимит адресного пространства
512 MiB и CPU 120 секунд. Продуктовый код и сервисы не менялись; платных
вызовов нет. Дисковый индекс — отдельная задача и внешняя зависимость;
в этой проверке производственный индекс не строился.

## Что измерено

GTFS SHA: `3b176d72280719f5e6f5fd8532a33e4e65e475acef9ad2419b61302822209295`.

| Данные | Количество | Представление |
| --- | ---: | --- |
| Узлы остановок | 8811 | ID → долгота, широта, название |
| Направленные соседние пары | 11230 | Пара stop IDs → множество линий |
| Связи пары с линией | 27504 | Множества route IDs |
| Узлы с исходящими рёбрами | 8758 | Списки смежности через множества |
| Полные исходные GTFS shapes | 28610 | Общие массивы double без копирования на каждое ребро |
| Точки shapes | 896979 | Долгота, широта, shape_dist_traveled |
| Прочитанные stop_times | 3553379 | Потоково, полная таблица в памяти не сохранялась |

Разные полные shape IDs здесь не трактуются как разные физические пути между
парой остановок. Геометрии загружены для измерения хранения, а не для утверждения
мультиграфа или выбранной модели сопоставления.

## Сколько памяти получилось

| Часть | Память |
| --- | ---: |
| Узлы, рёбра, связи с линиями и смежность | **9,20 MiB** |
| Общие компактные массивы всех shapes с метаданными словаря | **26,49 MiB** |
| Вместе | **35,69 MiB** |
| Временный lookup trip → route, удалён после построения | 15,23 MiB |
| RSS отдельного процесса после построения | **57,66 MiB** |
| Пиковый RSS процесса, включая накладные расходы измерения | **67,74 MiB** |

Логический размер объектов и RSS — разные величины: RSS включает интерпретатор,
буферы чтения, временные структуры и оставшуюся у аллокатора освобождённую память.
Рекурсивный подсчёт размеров сам создаёт временное множество посещённых объектов,
поэтому максимальный RSS является консервативным пиком всего исследования.
Потоковое построение и измерение заняли 16,337 секунды; это не benchmark
production-загрузки поверх будущего дискового индекса.

## Поместится ли в текущий деплой

Снимок перед измерением:

- API: 307 MiB, установленный лимит в текущем манифесте — 512 MiB.
- OTP: 2924 MiB.
- Хост: 11927 MiB всего, 6245 MiB доступно по free.

Сам вспомогательный граф не требует отдельной большой машины. Добавление
порядка 36 MiB хранимых данных или около 60–70 MiB самостоятельного Python-процесса
выглядит реалистичным при имеющемся запасе. Но это **не гарантия**, что любой
вариант интеграции поместится в 512 MiB API: пространственный индекс, кэш пробок,
рабочие буферы сопоставления и параллельные запросы здесь не измерялись.

## Границы будущего решения

- Не загружать все 3,55 млн stop_times и расписания в Python-словари ради графа.
  Детали рейсов получать ограниченными выборками из внешнего дискового индекса.
- Общие геометрии хранить один раз; не копировать длинную линию для каждого
  рейса, кандидата и шага обработки. Массив чисел и словарь на каждую точку
  имеют существенно разную стоимость.
- Согласованный TTL кэша 30 минут ограничивает свежесть, но не число записей и не память.
  Потребуется отдельный предел размера/вытеснение.
- Считать память на одновременно обрабатываемые маршруты и временные буферы,
  а не только размер постоянного графа.
- При смене графа/версии учесть кратковременное сосуществование старой и новой
  структуры; решение о загрузке и переключении пока не утверждено.

Это измерение отвечает на вопрос о масштабе памяти и не является разрешением
на реализацию графа, дискового индекса или алгоритма поправок.
